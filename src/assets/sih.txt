# Document Management Service — Frontend Project Context

## 1. Project Goal

I am building the **frontend for a Document Management Service**.

Tech stack:

* Vite
* React
* TypeScript
* Bun
* React Router
* Zustand
* Tailwind CSS

The backend already exists and is documented, but I don't want to wait for the backend to be fully ready.

Therefore, the frontend should work against:

1. A **mock/fake API**
2. The **real backend API**

The mock API should behave like the real backend as closely as possible.

### Core architecture

```text
UI
 ↓
Zustand Store
 ↓
Public Service
 ↓
 ┌───────────────┐
 │               │
Mock API      Real API
 │               │
 └───────┬───────┘
         ↓
     Same contract
```

The UI should **never call `fetch()` directly**.

The mock and real implementations should have the **same input/output shapes**, so switching from mock → real should not require changing UI code.

# 2. Backend

The backend is an Axum + PostgreSQL + S3/MinIO service.

Important backend concepts:

### Case

```ts
interface Case {
  id: string;
  name: string;
  created_at: string;
  updated_at: string;
}
```

### Document

```ts
type DocumentStatus =
  | "pending"
  | "processing"
  | "success"
  | "failed"
  | "finish";

interface Document {
  id: string;
  title: string;
  description: string;
  status: DocumentStatus;
  object_key: string;
  extracted_information: Record<string, unknown> | null;
  case_id: string;
  created_at: string;
  updated_at: string;
}
```

The mock `Document` must remain exactly this shape.

**Do not add fields like `file_url` to the mock Document.**

# 4. Document Upload Architecture

The real backend uses this flow:

```text
Frontend
   │
   │ 1. initiate upload
   ▼
Backend
   │
   │ creates pending document
   │ generates presigned PUT URL
   ▼
Frontend
   │
   │ 2. upload raw file directly
   ▼
S3 / MinIO
   │
   │ 3. confirm upload
   ▼
Backend
   │
   │ updates document status
   ▼
Document processing
```

The presigned upload URL is temporary.

The frontend should eventually simulate this lifecycle with the mock API.

# 5. Important Download/View Architecture

This has **NOT been implemented yet**.

The correct approach we decided on is:

Do **not** put:

```ts
file_url: string
```

inside the mock `Document`.

That would make the mock document shape different from the real backend response.

Instead, the backend's download endpoint should be represented as a separate service operation.

For example:

```ts
interface DownloadResponse {
  url: string;
}
```

Both mock and real implementations should return:

```json
{
  "url": "..."
}
```

The mock can return a fake/public PDF URL.

The real implementation will eventually call:

```text
GET /api/documents/{id}/download
```

and receive the real/presigned URL.

Then:

```text
User clicks document
        ↓
DocumentViewer
        ↓
getDownloadUrl(document.id)
        ↓
Mock OR Real API
        ↓
{ url: "..." }
        ↓
<iframe src={url} />
        ↓
PDF displayed
```

This is the **next thing to implement**.

# 10. API Layer

`services/api.ts` is responsible for actual HTTP requests.

Current idea:

```ts
const API_BASE_URL =
  import.meta.env.VITE_API_BASE_URL ??
  "http://localhost:8000";

export async function apiRequest<T>(
  endpoint: string,
  options?: RequestInit
): Promise<T> {
  const response = await fetch(
    `${API_BASE_URL}${endpoint}`,
    {
      headers: {
        "Content-Type": "application/json",
        ...options?.headers,
      },
      ...options,
    }
  );

  if (!response.ok) {
    const error = await response
      .json()
      .catch(() => ({
        error: "Something went wrong",
      }));

    throw new Error(
      error.error ?? "API request failed"
    );
  }

  return response.json();
}
```

```env

VITE_API_BASE_URL=http://localhost:8000
```

Config:

```ts
export const USE_MOCK_API =
  import.meta.env.VITE_USE_MOCK_API === "true";

export const API_BASE_URL =
  import.meta.env.VITE_API_BASE_URL ??
  "http://localhost:8000";
```

The goal is:

```text
VITE_USE_MOCK_API=true
        ↓
Mock implementation

VITE_USE_MOCK_API=false
        ↓
Real backend implementation
```

The UI should not know which one is active.

# 21. Important Architectural Rule Going Forward

Do not make the mock API "easier" than the real API by changing the data model.

For example, DON'T do:

```ts
Document & {
  file_url: string;
}
```

just because the mock needs a URL.

Instead model the actual backend operation:

```text
Document
   ↓
download endpoint
   ↓
URL
```

This keeps the frontend compatible with the real backend.

# 22. Development Philosophy

I want to build this **incrementally**.

Don't introduce:

* unnecessary abstractions
* excessive folders
* complex state management
* TanStack Query unless we actually need it
* premature architecture

Prefer:

```text
small feature
 ↓
make it work
 ↓
connect it properly
 ↓
move to next feature
```

The goal is a real, working frontend rather than an over-engineered architecture diagram.
